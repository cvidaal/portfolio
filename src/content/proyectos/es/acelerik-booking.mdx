<Seccion id="decisiones" etiqueta="Decisiones técnicas" titulo="Lo que no puede fallar en una reserva con pago">

<div class="dec">
<Decision titulo="Cero overbooking" abierta>

Si dos familias piden la última plaza a la vez, solo entra una. Dentro de la transacción de creación, antes de contar las plazas ocupadas, se toma un lock consultivo de PostgreSQL sobre la fecha y la hora de la franja. La segunda petición espera, cuenta después de la primera y, si la franja ya tiene sus 3 fiestas, recibe un 409.

```go
// internal/booking/repository.go · Create
tx, err := r.db.BeginTx(ctx, nil)
// ...
defer tx.Rollback()

// Lock the slot for the duration of the transaction
lockKey := item.Date + " " + item.StartTime
if _, err := tx.ExecContext(ctx, `SELECT pg_advisory_xact_lock(hashtext($1)::bigint)`, lockKey); err != nil {
	return Booking{}, err
}

var count int
if err := tx.QueryRowContext(ctx, `
	SELECT COUNT(*)
	FROM bookings
	WHERE date = $1
	  AND start_time = $2
	  AND booking_status <> 'cancelled'`,
	item.Date, item.StartTime,
).Scan(&count); err != nil {
	return Booking{}, err
}
if count >= maxParties {
	return Booking{}, errSlotFull
}
// ... INSERT de la reserva y de los cumpleañeros, en la misma transacción
```

</Decision>
<Decision titulo="Pagos sin duplicados">

Cada reserva crea su Checkout de Stripe con una idempotency key propia y, si ya hay un Checkout abierto, se reutiliza. El webhook verifica la firma, comprueba que la sesión pertenece a esa reserva y que importe y moneda coinciden. Un pago que llega tarde a una reserva cancelada se registra, pero nunca reabre la plaza.

</Decision>
<Decision titulo="Estados a prueba de errores">

Las reservas siguen una máquina de estados. El cambio se valida dentro de una transacción con `SELECT … FOR UPDATE` sobre la fila, así que dos cambios simultáneos no se pisan. Un cambio no permitido devuelve un 409.

</Decision>
<Decision titulo="Plazas que se liberan solas">

Una reserva sin Checkout caduca a la hora. Si hay Checkout, su caducidad en Stripe está alineada con esa misma hora y el webhook de sesión caducada cancela la reserva.

</Decision>
<Decision titulo="Listo para desplegar">

Dockerfile multi-stage, binario estático (`CGO_ENABLED=0`) en una imagen Alpine, ejecución con usuario no root, un endpoint `/health` que hace ping a la base de datos y la especificación OpenAPI generada por Huma y servida en `/docs`.

</Decision>
</div>

<p class="nota">Es una demo: el pago solo funciona con Stripe en modo de pruebas. El servidor rechaza crear Checkouts sin una clave de test y descarta los eventos en modo real.</p>

</Seccion>

<Seccion id="arquitectura" etiqueta="Arquitectura" titulo="Un proceso en Go y dos dependencias">

Un único binario (Gin con Huma) expone la API, sirve el frontend compilado y habla con PostgreSQL y con Stripe. El código se divide en los módulos `booking`, `payment`, `config` y `demo`.
