<Seccion id="problema" etiqueta="The problem" titulo="Birthday parties managed by phone and a notebook">

Kids' play centres manage birthday parties by phone, WhatsApp and a notebook: slots overlap, deposits are collected by hand and nobody knows what's free without asking.

</Seccion>

<Seccion id="v1" etiqueta="The v1" titulo="A first version to validate the idea">

The first version, Jungla Mágica, is a React web app with n8n flows and Supabase as the database ([jungla-admin repository](https://github.com/cvidaal/jungla-admin)). It was enough to validate the idea.

</Seccion>

<Seccion id="por-que-go" etiqueta="Why Go" titulo="It worked, but you couldn't touch it without fear">

<Evo v1="v1 · Jungla Mágica" v1Detalle="React + n8n + Supabase. The MVP that validated the idea." v2="v2 · Go API" v2Detalle="Business rules in code: typed, versioned and tested." />

<p style="margin-top:16px">Three reasons to rewrite it:</p>

- Go is the language I write code in.
- Code is easier to change with confidence than an n8n flow: it's typed, versioned in Git and testable.
- It's much cheaper to host: a static binary inside a small container.

</Seccion>

<Seccion id="decisiones" etiqueta="Technical decisions" titulo="What can't fail in a booking with a payment">

<div class="dec">
<Decision titulo="Zero overbooking" abierta>

If two families ask for the last slot at the same time, only one gets in. Inside the creation transaction, before counting the taken slots, a PostgreSQL advisory lock is taken on the slot's date and time. The second request waits, counts after the first one and, if the slot already has its 3 parties, gets a 409.

```go
// internal/booking/repository.go · Create
tx, err := r.db.BeginTx(ctx, nil)
// ...
defer tx.Rollback()

// Lock the slot for the duration of the transaction
lockKey := item.Date + " " + item.StartTime
if _, err := tx.ExecContext(ctx, `SELECT pg_advisory_xact_lock(hashtext($1)::bigint)`, lockKey); err != nil {
	return Booking{}, err
}

var count int
if err := tx.QueryRowContext(ctx, `
	SELECT COUNT(*)
	FROM bookings
	WHERE date = $1
	  AND start_time = $2
	  AND booking_status <> 'cancelled'`,
	item.Date, item.StartTime,
).Scan(&count); err != nil {
	return Booking{}, err
}
if count >= maxParties {
	return Booking{}, errSlotFull
}
// ... INSERT of the booking and the birthday children, in the same transaction
```

</Decision>
<Decision titulo="No duplicate payments">

Each booking creates its own Stripe Checkout with its own idempotency key and, if there's already an open Checkout, it's reused. The webhook verifies the signature and checks that the session belongs to that booking and that amount and currency match. A payment that arrives late for a cancelled booking is recorded, but it never reopens the slot.

</Decision>
<Decision titulo="Error-proof states">

Bookings follow a state machine. Each change is validated inside a transaction with `SELECT … FOR UPDATE` on the row, so two simultaneous changes can't overwrite each other. A change that isn't allowed returns a 409.

</Decision>
<Decision titulo="Slots that free themselves">

A booking without a Checkout expires after an hour. If there's a Checkout, its expiry in Stripe is aligned with that same hour and the expired-session webhook cancels the booking.

</Decision>
<Decision titulo="Ready to deploy">

Multi-stage Dockerfile, static binary (`CGO_ENABLED=0`) on an Alpine image, running as a non-root user, a `/health` endpoint that pings the database, and the OpenAPI spec generated by Huma and served at `/docs`.

</Decision>
</div>

<p class="nota">It's a demo: payments only work with Stripe in test mode. The server refuses to create Checkouts without a test key and discards live-mode events.</p>

</Seccion>

<Seccion id="arquitectura" etiqueta="Architecture" titulo="One Go process and two dependencies">

A single binary (Gin with Huma) exposes the API, serves the built frontend and talks to PostgreSQL and Stripe. The code is split into the `booking`, `payment`, `config` and `demo` modules.

<Seccion id="aprendi" etiqueta="What I learned">

That a booking is a concurrency problem: if two families press the button at the same time, only one can get the slot, and that's solved in the database, not on the screen. Also to treat payments as something that may arrive twice, late or never. And that moving from n8n to code gave me what I missed most: being able to change things without fear, because the tests warn me.

</Seccion>
